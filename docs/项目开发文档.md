# RAG-HC 项目开发文档

## 1. 文档说明

- 文档目的：用于支撑项目交接、二次开发、版本迭代、部署实施与内部汇报。
- 适用对象：前端开发、技术负责人、实施人员、测试人员、项目管理人员。
- 文档范围：覆盖项目定位、技术架构、目录结构、核心流程、模块设计、数据契约、环境配置、部署说明、风险分析与优化建议。
- 当前版本：V1.0
- 对应仓库：`/workspace`

## 2. 项目概述

### 2.1 项目定位

RAG-HC 是一个面向“检索增强生成（RAG）场景中幻觉检测与纠正流程”的前端可视化演示系统。项目通过终端风格界面、流程日志、知识块展示、评分趋势图和结果对比视图，模拟一个具备“回答生成、知识检索、差异检测、纠正迭代、结果呈现”能力的 RAG 纠错框架。

该项目当前更适合作为以下场景的演示载体：

- RAG 能力介绍或技术展示
- 面向客户或内部团队的概念验证
- AI 产品界面原型演示
- 幻觉纠正流程的可视化表达

### 2.2 建设目标

- 以较低成本快速呈现 RAG 幻觉治理的交互流程
- 用图形化方式表达“初始回答”与“纠正后回答”的差异
- 用统一的数据结构承载知识块、纠正步骤、日志和评分结果
- 为后续接入真实知识库、真实检索服务和真实评估服务预留界面与结构基础

### 2.3 当前实现边界

当前仓库是单页前端应用，未包含独立后端、数据库服务、鉴权体系和持久化模块。系统中的“检索”“纠正”“评估”是通过前端侧的模拟服务统一生成后再渲染展示，重点在于交互演示和流程表达，而非真实生产级 RAG 引擎。

## 3. 总体架构

### 3.1 架构特征

- 架构类型：前端单页应用
- 技术栈：React + TypeScript + Vite
- 展示方式：浏览器端渲染
- 数据来源：前端调用模拟服务生成结构化结果
- 图表能力：Recharts
- 样式方案：Tailwind CDN + 全局 CSS
- 音频能力：Web Audio API

### 3.2 逻辑架构

系统可划分为五个层次：

1. 展示层
   负责启动动画、输入面板、日志面板、知识块卡片、结果卡片、图表仪表盘和历史侧边栏等内容的可视化呈现。

2. 交互控制层
   负责用户输入管理、查询历史管理、视图切换、展开收起、过滤条件和弹窗控制等页面状态管理。

3. 业务编排层
   负责启动模拟、触发数据请求、处理成功失败结果、组织展示数据等业务流程。

4. 模拟服务层
   负责根据用户输入参数生成统一的结构化响应，包括初始回答、检索块、纠正历史、最终回答、幻觉评分和过程日志。

5. 基础运行层
   负责构建、模块解析、环境变量注入与本地开发服务启动。

### 3.3 运行流程

1. 页面加载后先进入 BIOS 风格启动动画。
2. 用户点击“初始化系统交互”后进入主界面。
3. 用户输入查询内容、数据库路径和最大纠正轮次。
4. 用户点击“执行序列”触发模拟流程。
5. 页面进入加载态，并同步刷新查询历史。
6. 模拟服务返回统一结构化结果。
7. 页面分别渲染初始输出、纠正后输出、知识块、纠正动作日志、过程日志和评分图表。
8. 用户可切换文本报告与数据仪表盘视图，并对知识块进行过滤与展开查看。

## 4. 技术栈说明

### 4.1 基础框架

- `react`
  用于构建组件化界面。

- `react-dom`
  用于浏览器端渲染挂载。

- `typescript`
  用于提升类型约束与可维护性。

- `vite`
  用于本地开发、构建与预览。

### 4.2 可视化与能力组件

- `recharts`
  用于构建雷达图、径向图、面积图、条形图等可视化组件。

- 模型接入 SDK
  用于访问当前仓库接入的外部生成式模型服务，生成演示所需结构化数据。

### 4.3 样式与体验

- Tailwind CSS CDN
  项目通过 `index.html` 中的 CDN 方式加载 Tailwind，适合快速演示，但不适合严格的企业级构建治理。

- 自定义全局样式
  在 `index.html` 中定义了 CRT、扫描线、故障风格、发光边框、滚动条等视觉效果。

## 6. 核心模块设计

### 6.1 入口模块

文件：`index.tsx`

职责说明：

- 获取根节点 `#root`
- 创建 React 根实例
- 将 `App` 组件挂载到页面
- 使用 `React.StrictMode` 提升开发期检查能力

### 6.2 主应用模块

文件：`App.tsx`

职责说明：

- 管理系统启动状态
- 管理输入参数状态
- 管理模拟结果状态
- 管理知识块展开状态与过滤条件
- 管理文本视图 / 仪表盘视图切换
- 管理查询历史
- 管理音频初始化、播放、暂停与音量
- 编排模拟流程并处理异常提示

页面主要区域包括：

- 顶部系统头部
- 左侧输入与流程日志区
- 右侧结果展示区
- 查询历史侧边栏
- 结果趋势详情弹窗

### 6.3 启动动画模块

文件：`components/BootSequence.tsx`

职责说明：

- 模拟 BIOS 风格开机流程
- 通过阶段状态依次展示内存检测、进度条和系统日志
- 在动画结束后触发主界面进入逻辑

设计价值：

- 提升演示氛围感
- 强化“系统启动”和“AI 中枢初始化”的产品感知
- 让主界面进入过程更具有仪式性和品牌识别度

### 6.4 输入组件模块

文件：`components/RetroInput.tsx`

职责说明：

- 统一输入框风格
- 对标签、占位符、输入值与变更处理进行封装
- 保持主页面中的参数输入区结构清晰

### 6.5 模拟服务模块

文件：`services/geminiService.ts`

职责说明：

- 接收 `SimulationParams`
- 组装系统提示语
- 调用外部模型接口生成 JSON 结果
- 基于固定的数据契约返回 `RAGResponse`

说明：

- 该模块是当前系统的“模拟引擎入口”。
- 尽管界面中展示了 Chroma 路径、RAG 检索和纠正流程，但这些能力在当前仓库中并非真实数据库调用和真实检索实现，而是通过统一模拟结果进行呈现。
- 后续若升级为真实系统，可将该模块改造成 BFF 接口调用层或直接替换为真实后端 API SDK。

### 6.6 类型定义模块

文件：`types.ts`

职责说明：

- 统一定义知识块、纠正步骤、过程日志、响应结果和输入参数的数据结构
- 为页面渲染、服务调用和后续扩展提供基础类型保障

## 7. 数据契约设计

### 7.1 输入参数

类型：`SimulationParams`

- `query`
  用户输入的问题文本，是整个模拟流程的核心驱动参数。

- `chroma_path`
  用于表达目标知识库位置的路径型参数，当前主要用于流程演示和提示语上下文。

- `max_correction_rounds`
  最大纠正轮次数，控制模拟结果中的纠正步骤深度。

### 7.2 检索知识块

类型：`RetrievedChunk`

- `id`
  知识块唯一标识。

- `source`
  知识来源，例如文档名、知识库分片名或逻辑来源标签。

- `content`
  检索到的知识文本内容。

- `relevance_score`
  相关度得分，取值范围通常为 0 到 1。

### 7.3 纠正步骤

类型：`CorrectionStep`

- `round`
  当前纠正轮次。

- `reasoning`
  本轮纠正原因或依据。

- `modified_part`
  被修正的回答片段或逻辑点。

### 7.4 过程日志

类型：`ProcessLog`

- `timestamp`
  日志时间戳。

- `level`
  日志级别，当前支持 `INFO`、`WARN`、`CRITICAL`、`SUCCESS`。

- `message`
  日志消息文本。

### 7.5 总体响应

类型：`RAGResponse`

- `initial_answer`
  初始回答，可能包含事实偏差或轻微幻觉。

- `retrieved_chunks`
  检索到的知识块集合。

- `correction_history`
  纠正动作明细。

- `final_answer`
  纠正后的最终回答。

- `has_hallucination`
  是否存在幻觉的布尔值标记。

- `llm_comparison`
  初始与最终幻觉评分对比对象。

- `process_log`
  本次流程的日志序列。

## 8. 页面功能说明

### 8.1 查询输入区

支持以下参数输入：

- 用户查询
- 知识库路径
- 最大纠正轮次

支持以下动作：

- 执行模拟
- 重置结果

### 8.2 查询历史侧栏

支持最近 20 条查询记录缓存于内存状态中，点击历史项后可直接回填并重跑流程。

当前限制：

- 仅保存在前端内存中
- 页面刷新后历史丢失
- 未支持用户级别持久化

### 8.3 结果对比区

用于展示：

- 初始输出
- 纠正后输出
- 初始幻觉评分
- 最终幻觉评分
- 优化趋势图

### 8.4 知识块展示区

用于展示：

- 检索来源
- 相关度得分
- 知识块正文
- 展开 / 收起状态
- 相关度过滤

### 8.5 流程日志区

用于展示：

- 加载中的动态流程提示
- 返回结果中的系统日志
- 按日志级别区分颜色和重点程度
- 调试日志显示与隐藏切换

### 8.6 仪表盘视图

用于展示：

- 多维性能雷达图
- 核心指标卡
- 径向总体置信度
- 幻觉率条形图

该视图适合汇报、演示和复盘场景。

## 9. 状态管理说明

当前项目采用 React Hook 在 `App.tsx` 中进行集中式本地状态管理，未引入 Redux、Zustand 或其他全局状态库。

主要状态包括：

- `booted`
  控制是否完成启动动画。

- `isLoading`
  控制流程执行中的加载状态。

- `params`
  管理输入参数对象。

- `result`
  管理模拟返回结果。

- `expandedChunks`
  管理知识块展开集合。

- `minRelevance`
  管理知识块过滤阈值。

- `showDebug`
  控制是否显示调试级日志。

- `viewMode`
  控制文本报告与仪表盘视图切换。

- `showTrendDetail`
  控制趋势图弹窗显隐。

- `showHistory`
  控制历史侧栏显隐。

- `queryHistory`
  管理查询历史列表。

- 音频相关状态
  包括音频上下文、主音量节点、循环调度器与播放状态。

## 10. 环境变量与配置

### 10.1 必需配置

- 模型服务访问密钥
  当前代码通过 `GEMINI_API_KEY` 读取模型服务密钥，并由 Vite 的 `define` 配置注入前端运行环境。

### 10.2 配置方式

在项目根目录新增 `.env.local` 文件，示例：

```bash
GEMINI_API_KEY=your_api_key_here
```

### 10.3 构建注入方式

`vite.config.ts` 中将环境变量映射为：

- `process.env.API_KEY`
- `process.env.GEMINI_API_KEY`

说明：

- 该方式适合演示阶段快速接入。
- 若进入生产环境，建议改为后端安全代理，不应在纯前端直接暴露高敏感密钥。

## 12. 部署建议

### 12.1 当前适合的部署方式

由于项目本质上是静态前端应用，因此可部署至以下环境：

- Nginx 静态站点
- 对象存储静态网站托管
- Vercel
- Netlify
- 企业内网静态资源服务器

### 12.2 推荐生产改造方向

若项目需要正式投入生产，建议增加以下能力：

- 新增后端服务或 BFF 层
- 将模型调用迁移至服务端
- 引入真实向量检索与知识库访问能力
- 引入鉴权、日志审计和调用配额治理
- 引入持久化查询记录与操作日志
- 增加异常监控和指标采集

### 12.3 Nginx 示例策略

- 将构建后的 `dist` 目录发布为站点根目录
- 配置单页应用回退到 `index.html`
- 控制缓存策略，区分 HTML 与静态资源
- 通过服务端环境注入或配置中心管理敏感信息

## 13. 代码质量与风险评估

### 13.1 当前优点

- 视觉风格鲜明，适合演示
- 类型定义较完整，数据结构清晰
- 图表表达丰富，展示效果较强
- 项目规模小，上手成本低

### 13.2 当前问题

- 主页面逻辑过于集中，`App.tsx` 承担了大量状态和视图编排职责
- 未建立自动化测试
- 未建立前端工程规范体系，例如 ESLint、Prettier、Husky
- 使用 CDN 注入样式资源，不利于离线构建和企业级发布治理
- 模型调用发生在前端，不适合高安全要求场景
- 查询历史仅保存在内存中，缺少持久化

### 13.3 风险清单

- 安全风险
  前端直连外部模型接口，密钥暴露风险较高。

- 可维护性风险
  业务逻辑集中在单一大组件，后期功能扩展容易引入耦合。

- 可测试性风险
  缺少单元测试与集成测试，升级时回归成本较高。

- 真实能力风险
  当前以模拟结果为主，若用于生产宣传或正式业务支撑，需要在文档和交付边界中明确“演示版”属性。

## 14. 优化建议

### 14.1 短期优化

- 将 `App.tsx` 拆分为页面容器、日志面板、结果卡片、仪表盘、历史侧栏、音频控制等多个子模块
- 抽离图表数据转换逻辑到单独的 `utils` 或 `view-model` 层
- 为服务调用增加超时处理、错误码映射和统一提示
- 将查询历史持久化到 `localStorage`
- 增加输入参数合法性校验

### 14.2 中期优化

- 引入真实后端接口
- 引入真实知识库与向量检索服务
- 增加用户登录、权限控制、审计日志
- 增加埋点统计和运行监控
- 建立自动化测试与持续集成

### 14.3 长期优化

- 引入多知识源接入能力
- 支持多模型评估与切换
- 支持结果导出、报告归档和分享
- 支持会话级追踪和批量评估
- 升级为可配置化 AI 评估平台

## 15. 二次开发建议

若后续希望将该项目升级为真实可用系统，推荐采用以下落地路径：

1. 保留现有前端展示层与视觉风格。
2. 新建服务端网关层，统一封装模型调用和知识检索。
3. 将当前模拟服务替换为真实接口调用。
4. 补充会话、任务、评估记录和结果归档数据表。
5. 增加用户体系、权限模型和管理端视图。
6. 建立测试、发布和监控体系。

## 17. 结论

RAG-HC 项目具备良好的演示价值和继续扩展基础，适合作为 RAG 幻觉治理场景的前端展示原型。当前版本的重点是“可视化表达”和“流程演示”，其下一阶段建设重点应放在真实能力接入、工程治理完善和安全架构升级上。对于需要快速汇报、概念验证和方案展示的场景，该项目具备较高的交付效率；对于需要进入生产环境的场景，建议按本文件中的优化路线逐步完成架构升级。
